## A. 门禁与判定类（来源 01）

### D-01 gate-failed 后人工"修复放行"是否需要二次机器判定
- **来源**：01 第 8 节问题 1
- **问题**：机器门禁重试耗尽（gate-failed）后升级人工，人工"修复产物后放行"时，是否需要再跑一次机器门禁？
- **选项**：A. 需要，修复只是提供新产物，仍须过门禁（防人工放行绕过规则）；B. 不需要，人工放行即终审
- **建议**：A（需要二次机器判定）。人工修复后的产物是新版本，没理由跳过校验；否则 gate 形同虚设。

### D-02 WARNING 的确认方式
- **来源**：01 第 8 节问题 2
- **问题**：WARNING 是否必须逐条点确认，还是允许"一键全部确认"？
- **选项**：A. 逐条确认（强制看到每条）；B. 允许一键全部确认（留痕）
- **建议**：B（一键确认 + 留痕）。WARNING 不阻断，逐条确认是摩擦；一键 + 留痕足够，且报告 unconfirmed 会披露未确认的 WARNING（R5-04）。

### D-03 规则集版本与模板版本的关系
- **来源**：01 第 8 节问题 3
- **问题**：机器门禁规则集（G/R 系列）是否独立版本化，还是跟随 pipeline.yaml 的 templateVersion？
- **选项**：A. 独立版本化（rulesetVersion 独立）；B. 跟随模板版本
- **建议**：A（独立版本化）。规则与流程演进频率不同：规则修复可独立发布，不必牵动整个模板；判定留痕里已经用了 rulesetVersion（02 第 9 节）。

### D-04 归档回读验证（R6-05）的触发成本
- **来源**：01 第 8 节问题 4
- **问题**：每次归档都跑"示例检索回读"会增加时间，是否只在知识库结构变更后触发？
- **选项**：A. 每次归档都回读（完整校验）；B. 仅结构变更后回读（成本优化）
- **建议**：B（结构变更后回读 + 定期抽检）。回读验证的是"格式=检索格式"这一结构性事实，结构不变则验证结果不变；每次跑是浪费。

## B. 流程与回环类（来源 02/03）

### D-05 门 B 回环的产物覆盖语义
- **来源**：02 第 14 节问题 1
- **问题**：澄清答复后重跑 [2] analyze，是"覆盖同一产物"还是"追加澄清答复记录"？
- **选项**：A. 覆盖产物 + 答复记录另存；B. 仅追加记录不改产物
- **建议**：A（产物覆盖 + 答复记录另存）。产物保持"最新确认版"单一事实，答复记录进检查点 history 供审计；与重入的产物历史（03 第 8.4 节）同构。

### D-06 D 门（用例评审）可配 auto 的边界
- **来源**：02 第 14 节问题 2
- **问题**：D 门默认 block，哪些项目可以降为 auto（低风险回归类）？
- **选项**：A. 不提供 auto，一律 block；B. 提供 auto 但须项目评审并带 review 标注
- **建议**：B（可配但需评审）。低风险回归项目逐次审用例是浪费；但放宽门必须有项目级评审背书，且审查降级记录进 unconfirmed。

### D-07 重入指令入口形态
- **来源**：02 第 14 节问题 6 / 03 第 9 节问题 1
- **问题**：用户发起重入的入口：ui-user-questions 弹窗还是独立命令入口？
- **选项**：A. 仅弹窗（人工门页面内操作）；B. 独立命令入口为主 + 弹窗为辅
- **建议**：B（命令入口为主）。重入是流水线级操作（涉及 cursor 回退与级联），应作为显式命令存在，弹窗适合已打开的人工门页面顺手操作。

### D-08 报告渲染入口归属
- **来源**：02 第 14 节问题 8
- **问题**：人读报告（02 第 12 节六段结构）由谁渲染？
- **选项**：A. mainAgent 代码渲染（report agent 只出 report.json）；B. report agent 产出渲染稿
- **建议**：A（代码渲染）。渲染是确定性工作，遵循"不放可计算指令进 prompt"原则；避免"LLM 解读完又让 LLM 写文档"的双重失真。

## C. 数据与存储类（来源 02/03）

### D-09 evidence 快照保留策略

- **选项**：A. 随流水线归档长期保留；B. 定期清理（按大小/时间）
- **建议**：A（长期保留）。报告、缺陷分析、审计需要长期可回放；存储成本用 03 第 6.4 节的大小策略（大文件摘要化）控制，不靠删证据。

- **建议**：B（后置）。用例 schema 还需要真实项目打磨；映射是存储适配层的事，接口已预留（02 第 7 节 CaseStore），不影响主流程。

### D-11 执行阶段的用例级超时取值

## D. 模板与注入类（来源 04）

### D-12 注入防护的"不可覆盖区"语法
- **来源**：04 第 7 节问题 1
- **问题**：公共骨架的边界条款放"输入内容之前"能否可靠防注入？是否需要独立"不可覆盖区"语法（如 `<<<不可修改>>>` 包裹）？
- **选项**：A. 保持文字条款（第 8 节输入安全段）；B. 引入不可覆盖区标记语法 + 解析时校验
- **建议**：B（引入标记语法，v1 先用文字条款过渡）。文字条款对大多数注入有效但对"高度对抗"输入不可靠；标记语法让模板解析器能断言"边界段未被覆盖"。建议 v1 文字条款 + 模板测试覆盖注入场景，标记语法列为 v1.1。

### D-13 模板 schema 内联 vs 外链
- **来源**：04 第 7 节问题 2
- **问题**：输出 schema 是内联进 prompt 还是外链文件？
- **选项**：A. 内联简版 + 外链全量；B. 仅外链
- **建议**：A（内联简版 + 外链全量）。内联保证 agent 不用额外读文件就能对齐关键结构；全量 schema 外链防 prompt 撑爆 token。05 模板已按此实现（第 3 节内联 + "完整 schema 文件"行）。

### D-14 审核模板的复核范围粒度
- **来源**：04 第 7 节问题 3
- **问题**：交叉检查是否需要按阶段列出"必查清单"，还是由审核 agent 自定复核面？
- **选项**：A. 按阶段列必查清单（如 analyze 必须查 boundaries/versionImpact/reuseSuggestions/openQuestions）；B. 审核 agent 自定
- **建议**：A（必查清单）。审核报告 schema 里已有 `checked` 数组，必查清单保证"查了哪些面"可对照；防审核 agent 漏审关键面（03 第 7.4 节）。

### D-15 extraContext 的最大规模
- **来源**：04 第 7 节问题 4
- **问题**：重入/回环时携带的人工答复/违规清单是否设 token 上限？超限截断策略？
- **选项**：A. 设上限 + 截断（保留最新 N 条）；B. 不设限
- **建议**：A（设上限，保留最新，附"已截断"标记）。extraContext 是阶段 agent 感知上下文的唯一渠道，但超长会挤占任务段注意力；上限建议 2K token，超限截断并在 extraContext 末尾标注。
